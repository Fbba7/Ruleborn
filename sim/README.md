# The simulation core

The heist simulation, written once and compiled for every target it runs on.
§24.7: *"the heist simulation is written once, in a library with no engine
dependencies, and both the phone and the server run that same compiled logic.
Writing it twice — once in the client's language and once in the server's —
would mean maintaining two implementations that must agree forever, and they
would eventually not."*

This is **T3.1, the determinism spike**, and **T3.2, the golden replays**. It
is not the game.

## What it proves, and what it does not

    bash sim/run_spike.sh

builds the crate for native x86-64 and for WebAssembly, runs a full 240-second
heist under both at five seeds, and compares the digests. They agree.

That is **two of T3.1's four targets**. §24.7 names four — desktop, server
(WebAssembly), a cheap Android and an iPhone — and the gate is *"identical
checksums on all four, or take the C# fallback without renegotiating"*. The two
that are missing need devices. What is settled is the half the task itself
calls load-bearing: *"put the server Wasm build in the first round rather than
deferring it — the whole architecture rests on the same code running in both
places."*

Native and WebAssembly are a real test rather than a tautology: different
instruction sets, different compiler backends, different calling conventions.
A divergence between them would be the same *kind* of divergence an ARM phone
would show.

## How determinism is obtained

| Hazard | What is done | Where |
| --- | --- | --- |
| Floating point differs between processors | There is none. Fixed point throughout: 64-bit with 32 fractional bits for positions, 32-bit with 16 for angles | `fixed.rs` |
| `sin` and `cos` differ between libm builds | A quarter turn of sine, computed in exact decimal arithmetic and checked in. Angles are a fraction of a turn, so π never appears | `trig.rs`, `sin_table.rs` |
| Square roots differ | Newton's method on integers, which terminates exactly | `fixed.rs` |
| Random numbers differ | SplitMix64 into xoshiro256++, one stream per subsystem, pure integer operations | `rng.rs` |
| Map iteration order differs | There is no map. Entities are vectors indexed by id, iterated in order | `lib.rs` |
| Overflow wraps on one target and traps on another | `overflow-checks = true` in release as well as debug | `Cargo.toml` |
| A phase reading another's half-finished state | The six phases run in §24.10's fixed order: inputs, laws, perception, movement, noise, states, checksum | `lib.rs` |

`no_floats.py` enforces §24.10's *"the simulation refuses to compile if one
appears"* — float types, decimal literals and float casts, over the crate's own
sources.

The sine table is generated by `build_table.py` and committed. It is never
computed at start-up, because computing it would need libm, which is the thing
being avoided.

## The replay format, and a number the document leaves open

§24.10: *"What is recorded — commands, never state. A move or an ability with
its tick, crew member and target. State is always recoverable by
re-simulating."* §24.11 adds what has to travel with it: *"reproducible forever
from four things: the seed, the input log, the island and the rules version."*
All four are in the header.

The same row sets a budget — *"under 2 kilobytes. About 120 bytes of header,
300 to 700 bytes of commands, and a checksum a second"* — and building it is
what shows the numbers do not all fit. A heist is 4,500 to 7,200 ticks, so
"a checksum a second" is 150 to 240 of them, and at the eight bytes a checksum
actually is:

    120 + 700 + 240 x 8 = 2,740 bytes

which is over the limit the same row sets. At four bytes it is 1,780 and fits.
**So the stored checksum is the low four bytes.** The full eight are still
computed every tick in memory, as the section requires; only the kept ones are
truncated, and a four-byte sum narrows a divergence to thirty ticks exactly as
well — a collision would have to land on the first second that differs, at one
chance in four billion.

Measured, with the command log the fixture draws: a 240-second heist with a
crew of five is **1,215 bytes**, and the longest of the four goldens is 1,215
of 2,048.

## Golden replays

`golden/*.rbh` are heists encoded by a build that is now history and committed.
`golden_replays_still_verify` decodes each one, re-simulates it, and compares.
A change that moves any number in the simulation fails and names the second it
moved at.

They are files rather than a test that regenerates them for the reason §24.9
is about: a test that computes its expected answer with the code under test
passes whatever that code does. Checking the bytes in means a rewrite that
needs them updated has to update them in a commit, where the diff is visible.

The harness was checked against a real regression rather than assumed to work:
changing suspicion decay from 20 to 21 a tick — the smallest plausible balance
tweak — fails at second 4 of 150.

## Layout

    src/fixed.rs      Fx (i64, 32 fractional bits) and Ang (i32, 16)
    src/rng.rs        SplitMix64 -> xoshiro256++, per-subsystem streams
    src/trig.rs       turn-based angles against the committed sine table
    src/sin_table.rs  generated, 1025 entries, exact at both ends
    src/lib.rs        the world, the six phases, the checksum
    src/replay.rs     the heist as bytes: header, command log, checksums
    src/tests.rs      the invariants the checksum rests on
    golden/*.rbh      replays committed today, re-simulated on every build
    src/bin/spike.rs  the native runner
    src/bin/golden.rs writes the golden replays
    wasm_spike.mjs    the WebAssembly runner
    no_floats.py      §24.10's float ban
    build_table.py    the table generator; runs once, output committed

## What the simulation contains

Enough of a heist to exercise every operation that can diverge, and no more:
§12.17's five guard roles with their cones and graded zones, three raiders on a
route, suspicion filling and draining at the document's rates, a realm law that
scales speed, and a noise roll. Every number in the fixture is the document's.

The crew is driven by the command log and nothing else — `commands_are_what_
drives_the_crew` asserts that with no commands nothing moves, because if the
crew moved on its own the input log would not be the whole record and §24.10's
"commands, never state" would be false.

The commands themselves are drawn from the seed rather than played by a
person: the spike needs a log long enough to matter and identical on every
target, and §12.6 budgets 15 to 25 decisions in a run, so the fixture draws in
that range. A recorded session would do the same job without being
reproducible from eight bytes.
