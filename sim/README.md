# The simulation core

The heist simulation, written once and compiled for every target it runs on.
§24.7: *"the heist simulation is written once, in a library with no engine
dependencies, and both the phone and the server run that same compiled logic.
Writing it twice — once in the client's language and once in the server's —
would mean maintaining two implementations that must agree forever, and they
would eventually not."*

This is **T3.1** (the determinism spike), **T3.2** (the golden replays) and
the buildable half of **T5.5** (pathfinding and crew control), and §12.17's line
of sight, noise, guard states and realm alarm. It is not the game.

## What it proves, and what it does not

    bash sim/run_spike.sh

builds the crate for native x86-64 and for WebAssembly, runs a full 240-second
heist under both at five seeds, and compares the digests. They agree.

That is **two of T3.1's four targets**. §24.7 names four — desktop, server
(WebAssembly), a cheap Android and an iPhone — and the gate is *"identical
checksums on all four, or take the C# fallback without renegotiating"*. The two
that are missing need devices. What is settled is the half the task itself
calls load-bearing: *"put the server Wasm build in the first round rather than
deferring it — the whole architecture rests on the same code running in both
places."*

Native and WebAssembly are a real test rather than a tautology: different
instruction sets, different compiler backends, different calling conventions.
A divergence between them would be the same *kind* of divergence an ARM phone
would show.

## How determinism is obtained

| Hazard | What is done | Where |
| --- | --- | --- |
| Floating point differs between processors | There is none. Fixed point throughout: 64-bit with 32 fractional bits for positions, 32-bit with 16 for angles | `fixed.rs` |
| `sin` and `cos` differ between libm builds | A quarter turn of sine, computed in exact decimal arithmetic and checked in. Angles are a fraction of a turn, so π never appears | `trig.rs`, `sin_table.rs` |
| Square roots differ | Newton's method on integers, which terminates exactly | `fixed.rs` |
| Random numbers differ | SplitMix64 into xoshiro256++, one stream per subsystem, pure integer operations — and none drawn by anything §12.17 describes, which "nothing here is random" forbids | `rng.rs` |
| Map iteration order differs | There is no map. Entities are vectors indexed by id, iterated in order | `lib.rs` |
| Overflow wraps on one target and traps on another | `overflow-checks = true` in release as well as debug | `Cargo.toml` |
| A phase reading another's half-finished state | The six phases run in §24.10's fixed order: inputs, laws, perception, movement, noise, states, checksum | `lib.rs` |

`no_floats.py` enforces §24.10's *"the simulation refuses to compile if one
appears"* — float types, decimal literals and float casts, over the crate's own
sources.

The sine table is generated by `build_table.py` and committed. It is never
computed at start-up, because computing it would need libm, which is the thing
being avoided.

## The replay format, and a number the document leaves open

§24.10: *"What is recorded — commands, never state. A move or an ability with
its tick, crew member and target. State is always recoverable by
re-simulating."* §24.11 adds what has to travel with it: *"reproducible forever
from four things: the seed, the input log, the island and the rules version."*
All four are in the header.

The same row sets a budget — *"under 2 kilobytes. About 120 bytes of header,
300 to 700 bytes of commands, and a checksum a second"* — and building it is
what shows the numbers do not all fit. A heist is 4,500 to 7,200 ticks, so
"a checksum a second" is 150 to 240 of them, and at the eight bytes a checksum
actually is:

    120 + 700 + 240 x 8 = 2,740 bytes

which is over the limit the same row sets. At four bytes it is 1,780 and fits.
**So the stored checksum is the low four bytes.** The full eight are still
computed every tick in memory, as the section requires; only the kept ones are
truncated, and a four-byte sum narrows a divergence to thirty ticks exactly as
well — a collision would have to land on the first second that differs, at one
chance in four billion.

Measured, with the command log the fixture draws: a 240-second heist with a
crew of five is **1,215 bytes**, and the longest of the four goldens is 1,215
of 2,048.

## Golden replays

`golden/*.rbh` are heists encoded by a build that is now history and committed.
`golden_replays_still_verify` decodes each one, re-simulates it, and compares.
A change that moves any number in the simulation fails and names the second it
moved at.

They are files rather than a test that regenerates them for the reason §24.9
is about: a test that computes its expected answer with the code under test
passes whatever that code does. Checking the bytes in means a rewrite that
needs them updated has to update them in a commit, where the diff is visible.

The harness was checked against a real regression rather than assumed to work:
changing suspicion decay from 20 to 21 a tick — the smallest plausible balance
tweak — fails at second 4 of 150.

## Islands, the rules version and the validator (the server's half)

§24.11: *"Any past heist — reproducible forever from four things: the seed,
the input log, the island and the rules version."* Until this, the header's
island was a placeholder and every heist ran on the one fixture realm. Now:

- **An island is a bundle** (`island.rs`). One canonical encoding, addressed
  by its SHA-256 (`sha256.rs`, checked against FIPS 180-4's vectors here and
  against Node's own SHA-256 on every island the server stores). `decode`
  refuses anything `encode` would not write, so one island has one hash.
  Each tile fact has one home: the ground layer carries §6.2's features,
  pace, surface, height, light and climbing aids; the Vault, the pylons and
  the Crystal Walls come from their own lists. Every world is built from an
  island — the fixture realm is `Island::fixture()` — and the goldens'
  command and checksum bytes did not move when that changed, only their
  headers, which now carry the real hashes.
- **Publishing rules** (`Island::check`): §5.2's ward limit, guard posts and
  law slots for the realm level, one thing a tile, an open edge tile to land
  on and at least half of each side open (F51, decided), and §6.1's route to
  the Vault from some open edge tile with every Crystal Wall standing. The fixture
  fails one of them on purpose — five posts where realm level 5 has three —
  and `Island::example()` is a legal realm-3 Heart for the server's tests.
- **Buildings on the grid** (§10.1, TD.36): an island may end with a list of
  buildings, each a code from `BUILDING_CODES` and its footprint's north-west
  tile — the Spire 3 by 3, the rest 2 by 2. `ground` lays `Feature::Building`
  on every footprint tile, which blocks feet and eyes and is a structure, not
  a wall, for Thorns; `check` counts each footprint tile as taken and bare.
  An island with no building writes no list, so every island before keeps its
  bytes and its hash; the table is in the rules version. The Vault still
  stands on one tile: its 3 by 3 would move every heist and the hold table
  measured on it (G45).
- **The rules version** (`rules_version`) is SHA-256 of the law table and of
  this build's digest of every golden heist. A number bumped by hand would be
  forgotten; this one moves whenever anything the goldens can see moves, and
  `golden_replays_still_verify` then fails until they are re-recorded under
  it. The server keeps one build per version (§24.11: "pin, do not patch").
- **The validator** (`verify_on`) checks that a replay names this island and
  these rules, is the shape §24.10 and §12.5 give a heist — 4,500 to 7,200
  ticks, a crew of three to five, commands in order, one checksum a second —
  re-simulates it and compares every second. The outcome is the
  re-simulation's; a replay carries no outcome at all.
- **The week's era travels with the heist** (`era.rs`, §18.3). A heist
  played in an era is written `RBH2`, with one byte more after the crew;
  one with none is `RBH1`, byte for byte as every replay before eras. The
  era is first on the rule sheet, as §7.3 orders: The Long Night's shorter
  sight, Glass Moon's see-through walls, Heavy Stars holding Half gravity's
  line off, Wildgrowth's stronger Life laws, Echoing Skies as a Revival
  source, Static Storm's stronger coil and Quiet Week's 30 seconds more. The
  era table, read by `build_laws.py` from each era's own rule, is part of
  the rules version (register G36, F49, D69).
- **The crew travels with the heist** (`ruleborn.rs`, §12.5, TD.12). A heist
  that carries its crew manifest is written `RBH3`: the era byte always (0
  for none), then each member's kind, form, level and traits, the Sage and
  the casts. Each member plays its kind's role, size band and ability; a
  heist with no manifest plays its crew by role, byte for byte as before.
- **The WebAssembly surface** (`ffi.rs`): numbers in and out and one shared
  buffer, which the host writes between calls. Still no imports.
  `wasm_spike.mjs` and the native `spike` both print a validator line — the
  rules version, the example island's hash, a replay recorded on it and the
  verdict — and `status.py` requires them to agree.

- **The landing is in the input log** (`Kind::Land`, §5.4). The raider
  picks an edge tile and the whole crew lands on it together, at tick 0,
  before any other command of that tick. Guards within 6 tiles start at 250
  of 1,000 suspicion unless the spot is in fog, darkness or tall grass —
  six steps walked, as every sound travels (§12.17), not through walls
  (`LANDING_HEARD_TILES`, `LANDING_SUSPICION`, gated against the document
  by `content_gate.py`). A late, second or inland landing is dropped, and
  `verify_on` refuses a heist that never lands (`Refusal::Landing`, -11
  over WebAssembly). `Island::landings` lists every open edge tile; `check`
  wants one of them, and a route from some open edge tile to the Vault;
  `Island::reaching` lists those the Vault can be walked to from, which is
  what the client's default landing picks among. Ghost tide returns a
  knocked-out crew member to the landing spot. The
  readings §5.4 leaves open are register G40; a Keeper who walls every edge
  tile but one is F51; the Heart's no-landing rule waits for universes
  (D71).

## Pathfinding and crew control

§12.18 specifies this more tightly than most of the document, and every clause
is load-bearing:

> *"Breadth-first on the tile graph with a fixed neighbour order, ties broken
> by tile index. Deterministic by construction (24.10)."*

**Breadth-first rather than A\*, and that is a decision rather than an
economy.** A\*'s answer depends on the heuristic, on tie-breaking inside the
open set, and on the order a priority queue returns equal keys in — three
places two correct implementations can differ. Breadth-first on a small grid
has one answer, and reaching it needs nothing beyond the neighbour order and
the tile index, both of which are stated.

**Four neighbours, not eight.** Breadth-first counts steps. With eight, a
diagonal step counts the same as an orthogonal one, which is false — it is
1.41 tiles of walking — so the "shortest" path would not be shortest. With
four, breadth-first is exactly shortest in the metric it counts. The order is
north, east, south, west, written out in one place, because changing it
changes every route in every replay ever recorded.

**Terrain slows the walk and cannot bend the route.** Breadth-first counts
tiles, so §6.2's "40% slower" changes how long a crossing takes and not which
way it goes. That is the spec's rule and not a shortcoming: a pathfinder that
routed around mud would be choosing for the player.

§12.18's other clauses are tests rather than prose:

| The rule | The test |
| --- | --- |
| "no automatic re-routing around a guard the player walked them into" | `a_crew_member_never_re_routes_itself` — 300 ticks, the route never changes without a command |
| "no picking a different door" | `a_sealed_goal_has_no_route_and_that_is_the_answer`, `a_route_into_a_wall_is_refused_rather_than_approximated` |
| "They pass through one another" | `crew_pass_through_one_another` — two crew sent to one tile both arrive |
| "The command, never the path" | the route is recomputed from the command and never encoded |

## Line of sight

§21.12: *"Sharp edges, no gradients. A tile is inside or outside."* So sight is
per tile, and the question is whether any tile between a guard and a target
stops it.

**Feet and eyes are separate properties of a tile**, because §6.2's features
pull them apart: a fence "blocks walking" and "doesn't block sight", a fog bank
is walkable and "blocks sight through it", a rock pillar does both. One flag
would make two of those three wrong. `a_fence_stops_feet_and_not_eyes` and
`a_fog_bank_stops_eyes_and_not_feet` are the tests that say so.

The line between two tiles is a **supercover** line — every tile the segment
passes through — with one rule for the case that needs one: a line exactly
through a corner counts both side tiles as crossed. That is a determinism
choice before it is a taste one. The common alternative steps in one axis on a
tie, which gives a different set of tiles from each end, so a guard could see
a raider whose line back says it is hidden. `a_line_is_the_same_from_either_end`
checks every pair of tiles in a 7x7 grid.

`walls_change_what_the_guards_notice` exists so this cannot be decoration: the
same heist with sight-blocking removed must produce different suspicion.

## Noise, guard states and the realm alarm

§12.17: *"Noise travels the way a crew walks"* — along the walkable path, never
through walls, *"so a guard turns toward the way around rather than toward the
source."* `noise::field` is the same breadth-first walk `path::find` uses, so
that heading is literal. A sound's reach is §12.17's metres converted to steps
a crew would take; a guard that hears one turns toward the neighbouring tile one
step nearer the source, which on the far side of a wall is the gap, not the
raider. `a_guard_turns_toward_the_way_around_not_toward_the_raider` puts a
raider directly behind the ruin wall and checks the guard faces the gap.

The six states sit on §12.17's thresholds. A rise is immediate; a fall waits
half a second (the document's floor, so a guard cannot flicker). Investigating
walks to the spot and searches it for ten seconds; Alerted, having lost sight,
searches for twenty; both then walk home as Returning, where a new sighting
re-raises them. An Alerted guard's call reaches every guard within four metres
half a second later. The realm alarm climbs once every thirty seconds to six,
plus one per knocked-out guard found; at five one more Warden walks in from
the entrance.

## No dice

§12.17: *"nothing here is random: a player who scouts an island can predict
exactly what will happen."* The spike broke that three times, each to put the
random generator on the hot path for the determinism test: a noise roll, a
random -1 to +1 on suspicion every tick, and a random direction for every idle
guard's turn each tick. All three are gone. A guard that is not walking now
turns steadily one way at its role's rate. The stream numbers stay taken so a
later subsystem cannot reuse one.

`the_seed_cannot_change_what_a_guard_does` holds this in place: the same
commands on seed 1 and seed 2^64-1 must give the same checksum every tick for
3,000 ticks. The seed still travels in the replay header, for the systems
§24.7 does give dice to — loot and island generation, not built — and for §8,
the one place the document asks for chance inside a heist: a dissonance's
gusts, flicker and déjà vu, Fair lights' illusions and Quicksand's pits draw
from their own stream, `Stream::Laws`, seeded from the replay, and draw
nothing in a realm where none of them sounds.

## Detection modifiers, roles and gaits

The rest of §12.17's modifiers. A raider in a guard's corner of the eye is
noticed at half the rate, over the same zones. Crouched halves the rate,
running multiplies it by 7/4, and an unlit tile halves it again. The factors
multiply and the one division comes last, so crouched in the dark is a
quarter, not a half of a half rounded twice. Standing still in tall grass is
invisible until a guard walks into the tile. Grass does not block sight past
it, as a fog bank does. Gravel and water carry sound five quarters as far,
and moss three quarters. That is applied to the radius before it is cut to
whole steps: walking on gravel reaches three steps, and a crouched walk on
moss reaches none.

Crew and guards move at §11.1's speed for their role — a Scout 4.5 tiles a
second, a Warden 2.6 — and a `Gait` command switches between walk, crouch and
run. Until v3.3 the document gave no speed for crouching or running, and
`CROUCH_PACE` (half) and `RUN_PACE` (double) were the simulation's reading.
v3.3's §12.17 took the same two numbers (G13), so the content gate now
compares them with `tools/design_facts.py` instead of listing them. The Python
harness answered the same gap differently — its crouch is §11.1's speed and its
run is double — and has not moved yet (D56). The harness
also gives the corner of the eye the far zone's rate at any distance, where
`content/detection.json` halves the zone's rate. This simulation follows the
content file.

Building this found a bug in the spike's movement. A character that reached a
tile centre part-way through a tick threw away the rest of that tick's step,
so everyone walked up to a tick per tile slower than §11.1 says. The Scout
managed 4.3 tiles a second, not 4.5.
`a_crew_member_covers_its_roles_distance_whatever_the_tile_edges` failed on
it (5.5 tiles where 5.7 is right), and `walk_route` now carries the remainder
on to the next tile.

## The Vault, the fight and the end of a heist

§12.6, §12.19, §12.20, §12.8, §5.4 and §12.9, in `heist.rs` (the numbers) and
in the states phase (the rules). Everything that moves a crew member between
Active, Down, Caught and Out happens in one fixed order each tick: guards'
hits → crew hits → knockouts → revives and captures → the Vault → loading →
the skiff → the clock.

- **The Vault.** It has 1,500 health per Vault level. It is cracked from a
  tile beside it, one hit every 0.8 s for Power, and Breakers deal double.
  While two or more crack it, every hit deals a quarter more: v3.3's assist
  bonus (§11.1), which also applies to pylons and wards. No guard hears it,
  as the owner decided (F35): v3.4's hit heard 5 m away and its call every
  five seconds of cracking to the guards within 5 m of the walk are gone;
  a guard that can see the crew still sees it. Once open, anyone told to load does so at 30 a second, until
  it reaches the player's target fill, fills its bag, or empties the exposed
  share. A loaded Carrier walks 15% slower.
- **Fights.** An Alerted guard beside a crew member hits it every 0.8 s for
  its §11.1 Power. The crew hits back when told to. A guard that has not
  noticed the crew is taken down: the swing is a two-second takedown, and if
  the guard is still Unaware when it lands, the guard is knocked out whatever
  either role (§12.8, v3.3; §29.1 orders the two). A guard that notices first
  takes an ordinary hit. Any other hit sends its suspicion to 1000. A
  knocked-out guard stays down; its body is seen exactly as a still crew
  member lying on its tile, so tall grass hides it, and a `Drag` command pulls
  it along at crouching speed. Another guard that sees it raises the realm
  alarm, once.
- **Capture.** At zero health a crew member drops its loot on the tile. It
  has ten seconds, and an ally beside it revives it in 3 s (a Mender in
  1.5 s). Anyone inside when the clock ends is caught.
- **The skiff** comes to an edge tile only, 20 s after the call at the Heart,
  and takes whoever holds the spot.
- **The escape's two decisions.** Loading stops when the clock left no longer
  covers getting out ("the crew loads to whatever that target and the
  remaining clock afford"). Getting out means the loaded walk to the skiff —
  or to the nearest edge if none is called — or the skiff's own arrival,
  whichever is later. The document gives no margin, so none is added; the
  Python harness adds 15%, which it calls chosen, not derived. `Drop` leaves a
  share of the load on the tile, which "costs exactly the fraction dropped"
  and frees a Carrier's pace only when the bag is empty.
- **§12.9's grades** follow from who got out with what: Clean, Loud, Partial
  or Foiled.

`planned()` is a heist played as a player would play it. v3.3 made it a
different heist: the crack noise then brought every guard to the Vault, so the
crew first takes down every guard it can reach unheard — the Scout, Breaker,
Mender and Carrier guards, from the moss behind each, the last one reached by
letting a Gravity Well pull the Breaker in and stepping round during its
reset. The Warden's rise has one ramp, in front of it, so the Warden is left.
All three then crack at once, Brittle stone doubling and the assist bonus
adding a quarter, and the Vault opens in 4.2 s, before that noise could
sound. The owner has since removed the noise (F35); the plan is kept.
The Scout and Breaker fill and leave; the Carrier fills its 300 on the
Vault's far side and leaves at 53 s. The outcome is **Clean**, 508 of 508. It is committed as `golden/planned-clean.rbh`, because the seeded
heists almost never open the Vault: 199 of 200 end Foiled.
`cargo run --release --example planned` prints it second by second.

### What building it found

Four things about the document, each pinned by a test rather than argued:

1. **§12.6's crack noise did nothing, and then it did everything.** v3.2's
   "every 5 seconds adds 100 suspicion" drained away in five ticks (F28).
   v3.3 made it a heard event that sends every guard in the Heart to the
   Vault — and no ordinary crack is shorter than five seconds, so a crew that
   has not cleared the Heart is found at the Vault. In the Python harness,
   whose crews do not, an optimal crew's success falls from 65% to 7.5% (F32).
   v3.4 gave the call a reach, 5 m by the walking path — the distance a hit
   was already heard at, so it added little to what every hit did (F35).
   The owner then decided no guard hears the Vault at all, and both are
   gone. (`no_guard_hears_the_vault_but_one_beside_it_still_sees`)
2. **§12.8's ambush has no way in on plain ground.** A crouched walk carries
   1 m and the tile behind a guard is 1 m away, so the last step of any
   approach is heard. The guard has then noticed, and "a guard that has not
   noticed the crew" is never reached. Crawling is silent in the table but
   has no control and no speed. Only a quiet surface lets you in. The fixture
   has moss behind two posts for that reason.
   (`a_crouched_step_up_behind_a_guard_is_heard_unless_it_is_on_moss`)
3. **"Cracking is 10 to 25 seconds" (§12.19) assumed a Breaker** (F30).
   v3.3 now says so and adds the assist bonus: a Breaker alone takes 15.2 s,
   a full crew 8 s and four with no Breaker 21.6 s, each exactly what §12.19
   states. (`cracking_takes_what_12_19_says_with_and_without_a_breaker`)
4. **§12.12 against §12.17.** "Guards' patrols shift slightly each run" sits
   beside "nothing here is random: a player who scouts an island can predict
   exactly what will happen". The two agree only if the shift is drawn once,
   at set-up, from the seed, and is visible to a scout. The fixture's guards
   hold posts, so the question does not arise yet.

And three bugs in this code, each caught by the trace or a test before
commit. An Alerted guard that converged onto a raider's own spot could not
see it: at zero distance the bearing is undefined and came out as east. The
Vault and the attack shared a swing counter and each reset the other's. And
idle guards turned at their full turn rate — a Scout through 240° a second —
which left no back to ambush. A posted guard now holds its facing.

It also needed two numbers the document did not give until v3.3, and both
are the document's now and compared by the content gate. A revived crew
member returns at 30% of its health (`REVIVE_HEALTH`, §12.20, G14), where the
simulation had read a quarter. The fixture's Vault holds 750 bag units
(`FIXTURE_EXPOSED`), a full five-crew's carry, which is §9.6's conversion at a
target's level median (G15); it had held 560, the sum of the old Carry
column.

## Laws and pylons

§7.3: "laws change a realm's rule sheet rather than containing special
cases". `build_laws.py` turns all 48 laws in `content/law_effects.json` into
`src/laws_table.rs` as exact ratios, so 1.25 becomes 5/4 and 0.65 becomes
13/20. The simulation cannot read JSON and decides nothing in decimals. The
table is committed, and the content gate regenerates it and fails on any
difference. The Python harness multiplies floats. This does not. The table
also carries `PARAM_COUNT`, which sizes the sheet: the sheet once held twenty
slots while the table named twenty-two, and weaving Thorns ran off its end.

Each tick the laws phase — §24.10 puts it second — builds the sheet from the
laws whose pylons still stand. Everything downstream reads it:
- crew, guard and loaded speed, climbing and leaping;
- sight range, suspicion fill and decay, and noise radius;
- damage to structures and in fights;
- the alarm's spread;
- the heist clock ("Haste: the heist clock runs 25% faster");
- Glass ("walls become see-through") and Stillness ("standing still for 1.5
  seconds becomes invisible");
- healing once a second, each rule its own parameter (F31): `ally_healing`
  (Kinship) for anyone beside an ally, `structure_healing` (Regrowth) for
  guards, wards, pylons and the Vault.

v3.4 makes the rest of the launch 24 rows on the same sheet (§7.3), and each
is a parameter here too, named for the rule rather than the law, so nothing
asks which law set it:
- `slide` and `rebound` (Frictionless, Bounce): a crew member at the end of
  its route slides on until a wall or a body stops it; with a rebound, the
  first wall sends it back once, and a blow on a ward returns half to the
  striker. Wardens absorb rebounds.
- `large_health`, `large_speed`, `small_health`, `small_speed` (Density):
  health and speed read by size. The crew and guards are roles, so the Warden
  reads as large and the rest as standard.
- `effect_delay_seconds` (Delay): a triggered ward's effect lands three
  seconds after it fires, and a guard changes state three seconds after it
  is triggered (G23).
- `light_band_seconds` (Aurora): a band two rows deep crosses the realm every
  ten seconds; inside it sight doubles, outside it halves.
- `chain_share` (Chain lightning): a hit jumps to the nearest of the struck
  one's side within three tiles at half strength.
- `touch_stun_seconds` (Static): five tiles walked charge a character, and the
  next one it touches is stunned for half a second.
- `revival_return` and `revival_swap` (Echoes, Soul swap): §7.3's Revival row.
  A knockout returns once at 60%, or the one about to fall swaps with its
  nearest ally, who takes half the blow; the higher N applies, once.
- `touch_damage` (Thorns): standing on or beside a wall or a live hedge costs
  5% of full health a second.
- `regrow_seconds` (Bloom): a cut Thorn Hedge is whole again after ten
  seconds.

Where a law's sentence stops short, the reading is named beside the code and
listed in G23; `regrow_seconds` is one name for more than one rule (G24).

The simulation reads 31 of the sheet's 34 parameters. The other three are
named by the gate: Soul lanterns' `unlit_drain`, which needs lantern light,
and carry weight and cone angle, which no law sets. The gate fails on any
sheet parameter the simulation neither reads nor names, and on a named one
the sheet no longer has.

A Law Pylon has 600 health (§10.2, level 1). Whoever is told to break one hits
it from beside it, and a Breaker hits for double. At zero, its law is off from
the next tick — the same tick on every machine — and its page is the crew's.

The laws belong to the heist, not the world: §24.11 says a replay "records the
exact set of laws it was made under". `World::from_heist` weaves them, and the
replay header's rules field is now a digest of the law list and where each
pylon stands, not placeholder bytes. The fixture realm runs Haste, Brittle
stone and Glowing dark, the three §5.2 allows at realm level 5. The planned
heist breaks Haste's pylon on the way in, so the clock stops running fast,
and it still ends Clean with every bag full and one page.

The spike's old stand-in law, which slowed the crew by a tenth every two
seconds, is gone.

## Resonances and chords

§8: what the laws in a realm do together. `combos.rs` works out, each tick
from the laws whose pylons stand, which combinations sound — so breaking a
pylon silences every combination its law was part of from the next tick, as
it silences the law. `build_laws.py` generates each law's notes, the 44
resonance pairs and the 12 chords' notes from content, and the rules version
covers all three tables.

- **Harmonies** (two laws sharing a note) strengthen the shared kind of
  effect on both laws by a quarter: Flow and Weight their speeds, Spark damage
  and stuns, Bloom healing and regrowth (a regrowth a quarter sooner), Echo
  returns and rebounds. Glow deepens Aurora's band by two rows and Hush lets
  the crew hide a tile closer. Veil has nothing to lengthen at launch.
- **Dissonances** (opposite notes) add their effect: Gusts and lulls moves
  everyone's speed ±20% every ten seconds, Flicker makes the realm bright or
  dark for three seconds every fifteen, Wildfire burns grass and hedges a spark
  lands on, and Déjà vu draws the guards to an illusion once a heist.
- **Signature resonances**: all twelve that join two launch laws (§8.4), from
  Pinball's ricochets to Northern lights' bands being the only light.
- **Chords** (three notes from three distinct laws, §8.8): all twelve, from
  Tempest's speed and lightning to Rebound's bounced stuns.

The fixture realm's three laws make three combinations — a Spark harmony
(Brittle stone's double becomes 2.25), Night runners (Haste and Glowing dark:
everyone 30% faster in the dark) and the Wild hunt chord (running is silent).
The planned heist breaks Haste's pylon on the way in, which silences all three,
and still ends Clean with every bag full.

A chord's cost in stability, and every combination's discount or surcharge,
is the economy's, not the heist's; the simulation plays the laws a bundle
carries, and a bundle carries no crown laws yet (D61). Where a row stops short
of a rule the reading is G25's, named beside the code and held by a test —
one per combination, which `sim/systems.json` maps and the completion report
counts.

## Abilities

§12.6: *"each ruleborn's ability has two uses a heist, with a lockout of one
decision slot (10 seconds) between them, and no cooldown"*, and *"At most four
abilities are ready at once."* The Ability command (12 on the wire) names a
crew member and a tile; the ability fires if it has a use left, is one of the
ready four and its character can act, and spends a use only if it does
something. The ready four are worked out before each tick's inputs: one
whose lockout ends while four are ready waits, and the waiting take their
turn in the order they came free.

Fifteen of §11.11's eighteen are built, each a named number changed for its
stated time and each with a test: the Stormhound's sprint, the Skyskipper's
satchel, the Tidewalker unhindered, the Quarryback's pound, the Emberling's
burst, the Hourkeeper's rewind, the Stillwatch's freeze, the Mossbear's root,
the Bloomling's heal, the Echoplate standing over the crew, the Soulmender's
link and the Sparkwright's cut to the Sage's cooldown; and, over §6.2's gaps
(a pond, a lava crack, stepping stones nobody can leap), the Featherkin's
glide, the Rambler's charge and the Rootrunner's root bridge. A bridge is a
timed mark on the grid's gap tiles (`Grid::is_bridged`), walkable by anyone
while it stands; whoever is on it when it goes is put back on the end it was
laid from. Their numbers are read out of `content/ruleborn.json`'s own
sentences by `content_gate.py`, the table's rows held to its ids, roles, sizes
and fliers. The root's half damage and the link's sharing are applied to what
each crew member lost since the last share, before knockouts are settled, so
every source of damage passes through them. The other three wait on what they
act on (`Ability::built`), and what the document leaves open about all of
them is register G77 and G81.

The Sage (§11.7) comes with the manifest. The Sage command (13 on the wire)
names a power in the crew-member nibble and a tile; after any power the Sage
*"cools down for 20 seconds before it can use another"*, and each power has
its level-1 uses. Eight of the twelve launch powers are built: the
Archivist's Suspend, Reveal and Recall, the Tinkerer's Jam and Plank, the
Gardener's Renew and Decoy, and the Wanderer's Tailwind. Vine bridge waits for
a command that names two points, Rift for universes of several realms, Invert for a rule on which
parameters have an opposite, and Copy for a law that applies around the crew
rather than over the realm (`Power::built`).

## The event log

§24.10: *"Beside the replay the simulation keeps an event log ... outside the
checksum, so a result can name a moment without changing what is
replayed."* `events.rs` is that log: every guard state change with its cause,
knockouts and returns, captures and boardings, the alarm's levels and why,
wards fired, pylons, the Vault, a suspended law, abilities and Sage powers,
and every crew member's position once a second. Nothing in the simulation
reads it back and `checksum` never sees it, which
`the_log_is_outside_the_checksum` holds. §12.13's decisive moment is chosen
from it by rule (`Log::moment`).

## Wards

§10.3's six wards at level 1, built to `docs/design/spec/wards.md` (G3's
drafted resolution), which gives each ward one of three kinds:
- **Passive.** Crystal Wall is a wall with 800 health until it is broken.
  Thorn Hedge is passable and costs 5% of full health a second.
- **Aura.** Static Coil shocks everyone within 2 tiles every 3 seconds.
- **Triggered.** Gravity Well, Time Snare and Lantern Glare fire on the first
  crew member in reach, then stay inert until they reset.
  - A Gravity Well pulls everyone within 3 tiles to its centre and holds them
    2 seconds. Their route is recomputed from there to the tile they were sent
    to: the order was the tile, not the path.
  - A Lantern Glare shows the crew for 5 seconds to every guard within the
    alarm's spread reach of it, 4 m (F33, decided; §10.3 says "every guard
    in the realm"), and blinds the crew for 2. Each Glare holds its own
    reveal, so a second one firing does not take the first's away.
  - Under Delay, a guard's rise to Suspicious, Investigating or Alerted —
    on its own suspicion, a lure, or the alarm's spread — lands its delay
    after it was triggered, as a ward's effect does (G23). A rise queued
    before Delay's pylon breaks still lands at its tick. A regrow time takes
    the shortest applied (G24).

A ward can be disarmed from beside it: 3 s + 1 s a level, silent, cancelled
by moving, and never reset. Or it can be smashed, loudly, with Breakers
doubled.

The document's numbers are read out of `content/wards.json`'s own sentences
by the content gate: a rewording that stops a number parsing fails there. The
two numbers the spec had to add are the document's since v3.3: Static Coil's
8% a shock is compared, and ward health is 550 a level. §10.3 also still says
500 in its first paragraph (C34), so that one stays listed as a reading, with
the reason. So does "blinds them", read as a crew unable to act.

v3.3 changed four ward and fight rules, and they are ported (D56). Disarming
is fifteen seconds standing on the ward's tile, restarting if the disarmer
steps off. v3.4 answered G16: a ward's sensor ignores the crew member standing
on its tile to disarm it, and fires on anyone else. It says nothing of the walk
there, so a Lantern Glare, which fires within 2 tiles, still shows the crew to
every guard as its disarmer arrives; that reading is G18, and a test pins it.
The ambush and the Vault's silence (F35) are under the Vault and fights below.

Reset times come from §10.3 — Time Snare 12 s, Lantern Glare 20 s — although
§10.2's Ward row gives every ward 10 s at level 1. Building this found that
contradiction (C32). The fixture puts one of each ward in the south half of
the realm, where the planned heist does not go.

## Height

§6.2's raised ground runs from 0 to 3 levels.
- **Climbing one level** needs a ramp, stairs or vines on either tile, or a
  law that lets anyone climb (Honeycomb, or Half gravity's leap). Two levels
  at once is a cliff.
- **Dropping** is "free and one-way", so the pathfinder's steps are now
  directed: a route can go down a cliff that no route comes back up.
- **Landing** is heard 2 m off from one level and 4 m from three (§12.17).
  §12.17 gives nothing between, so two levels is 3 m, listed as the
  simulation's reading.
- **Sight** follows §12.17, which §12.8 says wins. A guard a level higher
  sees a metre further per level, and one looking up loses its far zone
  entirely. §6.2's table says higher ground sees "2 tiles further per level".
  Building this found that, and two more places where §6.2 restates §12.17
  differently: tall grass and gravel (C33).
- **Sound** ignores height and travels any walkable path both ways: a cliff
  stops feet, not noise.
- **A pit** is a tile whose floor is one level below the ground it is dug in
  (`Grid::level`): walking in is a free drop, heard as a one-level landing,
  and walking out is a climb. **An updraft vent** lets anyone stepping off it
  go a level up, two under Half gravity.
- **Looking down.** A guard higher than an arch's tile cannot see whoever is
  under it, and a guard cannot see the foot of its own cliff: the tile right
  below an edge, looked at over that edge (a ramp is not a cliff). Both are
  readings, G80's.

The fixture puts the Warden's post on a one-level rise with a ramp up from
the north.

## The simulation against the content file

`content/detection.json` holds §12.17 as data; the simulation holds the same
numbers as Rust constants, because §24.7 forbids reading decimals where a
result is decided. Two copies of one fact drift, and they had: the first
fixture had the Scout's zones at **half** §12.17's size — 1, 2 and 3 metres for
2, 4 and 6 — and nothing noticed until the guard work reread §12.17 by hand.

`content_gate.py` compares the 98 values the simulation carries against
`detection.json`, `roles.json` and — for the §12.6, §12.19, §12.20 and §5.4
numbers that have no content file — `tools/design_facts.py`, which is now
their one home; the Python harness imports them from there. It walks every number in both files, and
each has to be compared, named as not modelled yet, or named as derived from
one that is. Anything else fails the gate. The first version only *said* this,
and the peripheral modifier sat in the file neither compared nor listed. The
self-test plants seven faults and must catch all seven: the halved Scout, a
moved state floor, a deleted role, a wrong multiplier, a slow Scout, an
uncompared number and a deleted test.

## How progress is reported

`status.py` runs every gate — the float ban, the content file, every test by
name, the goldens, native against WebAssembly — and writes `status.json`. `systems.json` says
which tests prove which system. The audit page's **What is built** band reads
the two: a system shows as built only if every test naming it passed on the
last run, and a renamed or deleted test makes it read *proof missing*, never
built. `status.py` also fails if a test belongs to no system or a system names
a test that does not exist, so the band cannot drift from the code.

## What the simulation contains

A whole heist in one realm: §12.17's five guard roles on their posts, a crew
of three to five in §11.1's roles, sight, sound, the six guard states and the
realm alarm, the Vault, fights, capture, the skiff, three woven laws with
their pylons and what they make together, and §12.9's grade at the end. Every number in the fixture is
the document's except the ones listed as the simulation's reading, and
`content_gate.py` checks that rather than this sentence asserting it.

And a heist across a universe (`universe.rs`, §5.4): the crew lands on an
outer realm and goes realm by realm along the shortest route to the Heart,
each outer realm's Vault its way on, one world at a time with the clock, the
Sage and the casts carried across; the Wanderer's Rift opens back to a realm
the crew has been in. An overloaded universe's crew may enter at a fault,
straight to the Heart, and its laws flicker. `rb_verify_universe` verifies one
as `rb_verify` does an island, and the readings are the register's G87 and
G88.

The crew is driven by the command log and nothing else — `commands_are_what_
drives_the_crew` asserts that with no commands nothing moves, because if the
crew moved on its own the input log would not be the whole record and §24.10's
"commands, never state" would be false.

The commands themselves are drawn from the seed rather than played by a
person: the spike needs a log long enough to matter and identical on every
target, and §12.6 budgets 15 to 25 decisions in a run, so the fixture draws in
that range. A recorded session would do the same job without being
reproducible from eight bytes.
