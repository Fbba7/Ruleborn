# Run fewer agents behind calibrated, independent gates

The evidence supports this project's basic shape: one lead coordinating isolated workers. It also says the last waves failed on three problems that more agents cannot fix. Agents graded their own work; they shared files and unwritten design decisions without contracts; and they ran oversized contexts against one shared usage pool. Published measurements show agents overrating their own success by roughly two to four times. In one study Claude agents predicted 61% success against a real 27%, the same shape as this project's 80–99% self-scores against a roughly 30% audit. Centralised coordination holds error amplification to 4.4×, against 17.2× for uncoordinated agents. A single LLM integrator still becomes the bottleneck unless merging is mechanical. On cost, every request re-reads the whole context, so a session at 350k tokens pays about 3.5× more per tool call than one at 100k, and it also recalls less. The levers that cut spend without cutting quality are four: cap context near 200k, restart at task boundaries with written handoffs, send routine work to Sonnet 5.5 at half Opus price, and keep screenshots and test logs out of the main context. LLM judges are weakest at the format the art director uses now, absolute 0–5 scores. Before they block merges, they need pass/fail criteria per quality, pairwise comparison against golden screens the owner has approved, repeated sampling, and calibration against 30–60 owner labels, measured by how many failures they catch. For the next UI wave, run at most five builder sessions at once, plus the lead and short gate runs. Build the UI kit and golden set before the screens. Put the lead, art director, artists and initial kit design on Opus 5.5, and the screens and later kit work on Sonnet 5.5. Spend the owner's time on the golden set, the plan and sampled blind audits, not on approving items one by one. Much of the evidence comes from vendor engineering reports and search-summary readings of papers rather than controlled studies, and each claim below is labelled accordingly.

## Most evidence here is engineering reports, not experiments

The evidence base is thin in controlled studies and rich in first-party engineering accounts. Each claim below carries one of five labels. **Measured** means a controlled or quantified study. **Reported** means a first-party engineering account with numbers but no comparison condition. **Vendor guidance** means documentation advice. **Opinion** means a practitioner judgement. **Inference** means my own reasoning from the sources. Several academic and practitioner sources (arXiv, Cursor, Cognition, METR, GitHub docs) could not be fetched directly. Their figures come from search-result summaries, and the report says so where a figure carries weight. Anthropic's engineering posts and the Claude Code documentation were read in full. Prices, plan limits and Claude Code behaviours change often, so re-check them before relying on them.

## A coordinated hub beats a peer swarm, but only with mechanical merges

The strongest quantitative result favours a coordinator over flat peers. Google Research tested **180 agent configurations** across three model families and four benchmarks. Independent agents with no coordinator **amplified errors 17.2×** relative to a single agent. Centralised coordination held this to **4.4×**, because the orchestrator acts as a "validation bottleneck". Coordination improved parallelisable tasks by about **+80.9%**, while every multi-agent variant **degraded sequential-reasoning tasks by 39–70%** (measured, via search summary) ([arXiv 2512.08296](https://arxiv.org/abs/2512.08296v1); [Google Research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)). Anthropic's research system, an Opus lead with Sonnet subagents, beat a single Opus agent by **90.2%**. Token usage alone explained **80% of performance variance**, and multi-agent runs used about **15× the tokens of a chat**. Anthropic's own caveat is that "most coding tasks involve fewer truly parallelizable tasks than research" (measured and reported) ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). So multi-agent setups win largely by spending more tokens in parallel, and coding, unlike research, mostly cannot spend them in parallel.

The practitioner reports agree on the shape and add a warning about integrators. Cursor found that flat, equal-status agents sharing locks became risk-averse: **20 agents delivered the throughput of about 2–3**, and agents that died while holding locks caused deadlocks. A planner/worker/judge hierarchy, in which workers ignore each other and each cycle starts fresh, worked far better. A dedicated integrator agent "created more bottlenecks than it solved" and was removed (reported, via search summary of a mirror) ([Cursor](https://cursor.com/blog/scaling-agents); [ZenML](https://www.zenml.io/llmops-database/scaling-multi-agent-autonomous-coding-systems)). Anthropic's 16-agent C compiler had no orchestrator at all. It produced a 100k-line compiler that builds Linux 6.9, over about 2,000 sessions and just under $20,000. It worked because a near-perfect test suite supplied many independent failing tests. On the one indivisible task, "all 16 got stuck on the same bug… then overwrote each other's changes" (reported) ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). Cognition's April 2026 update narrows its earlier "don't build multi-agents" stance. What works, it says, is "multiple agents contribute intelligence to a task while writes stay single-threaded" (opinion, via search summary) ([Cognition](https://cognition.com/blog/multi-agents-working)).

For this project the lead/worker design is right. Two things follow (inference). The lead should plan, triage and validate rather than resolve merges by hand. Workers should rebase onto main and pass CI themselves, so the agent that holds the context resolves its own conflicts, as in the C compiler pattern. Game UI is also the hard case. Cognition's thought experiment has one agent building the background and another the bird, with the merging agent inheriting their clashing style assumptions ([jxnl.co summary](https://jxnl.co/writing/2025/09/11/why-cognition-does-not-use-multi-agent-systems/)). That is the same failure as artists, kit and screens working in parallel without a frozen style and component contract. Past roughly five to eight workers, a single LLM lead should hand subsystems to sub-leads, as Cursor's sub-planners do. That threshold is inference, since no study measures an LLM lead's span of control.

### Independent reviewers are the only documented cure for self-grading inflation

Agents' self-assessments are reliably inflated, and the size of the inflation matches what this project saw. Agents that succeeded **22%** of the time predicted **77%** success. After execution, Claude agents predicted **61%** against an actual **27%** (measured) ([Lacuna summary of Kaddour et al.](https://lacuna.tiptreesystems.com/work/agentic-uncertainty-reveals-agentic-overconfidence/wrk_eb7c163696073ae3de53b16496a81db1)). False success claims caused **45–48% of failures** in tau2-bench domains and **75.8%** in AppWorld trajectories with explicit status claims, and LLM judges struggled to detect them (measured, via search summary) ([arXiv 2606.09863](https://arxiv.org/html/2606.09863)). In evolutionary search, self-reports **overstated success by 4.8–9.3×** ([arXiv 2609.00652](https://arxiv.org/html/2609.00652v1)). Self-correction without outside feedback does not help either. Two rounds of intrinsic self-correction took Llama-2 on GSM8K from **62.0% to 36.5%**, because models change right answers into wrong ones (measured) ([Huang et al., ICLR 2024](https://arxiv.org/abs/2310.01798)). Models also prefer their own outputs, and the bias rises with how well they recognise their own text (measured) ([Panickssery et al., NeurIPS 2024](https://arxiv.org/abs/2404.13076)).

Anthropic's harness work turns this into a design. "Agents reliably skew positive when grading their own work," and it is "far easier to tune a standalone evaluator to be skeptical than to make a generator critical of itself." Out of the box, the Claude QA agent found real issues, "then talked itself into approving the work". The fix was to read its logs and edit its prompt wherever its judgement diverged from a human's. "Sprint contracts", in which generator and evaluator agree hard pass thresholds before building (27 criteria in one sprint), stopped premature completion. The costs are concrete: a solo run took 20 minutes and $9 and produced a broken app, while the full harness cost $200. On Opus 4.6 it fell to **$124.70, with QA passes at $3–4 each** against $5.88–$71 per build round (reported) ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)). Independent review is therefore cheap relative to building. Claude Code's guidance adds three rules (vendor guidance) ([Claude Code docs](https://code.claude.com/docs/en/best-practices)). The reviewer should be someone "who didn't write the code". Its tools should be limited to `Read, Grep, Glob`, which enforces read-only rather than requesting it. Its scope should be narrow, because "a reviewer that's asked to find problems will always find *something*." One consequence is easy to miss (inference). The lead approving its own integrated build is also self-assessment, so the art-direction gate must be independent of the lead too.

## Contracts and single owners prevent the collisions that branches cannot

Separate branches and containers stop agents overwriting each other's files, but not semantic conflicts. Version control "will only protect you from textual conflicts" (opinion, via search summary) ([Fowler](https://martinfowler.com/bliki/SemanticConflict.html)). Practitioners report worktrees merging cleanly two plans that cannot both be true. Lockfiles and shared fixtures silently drop changes, and agents edit files outside their task (opinion) ([dev.to](https://dev.to/naw103/running-multiple-claude-code-agents-in-parallel-what-worktrees-cannot-see-4le7)). Two 2026 benchmark papers report patches that "pass alone, fail together", and agents that promised to stay apart still edited the same line (measured, unverified search summary) ([arXiv 2609.25396](https://arxiv.org/pdf/2609.25396); [arXiv 2607.21909](https://arxiv.org/pdf/2607.21909)). The merge that silently undid the database optimisation is a textbook semantic conflict. In order of strength, the defences are as follows (inference from documented practice). First, a test that encodes the optimisation's intent: GitLab's QueryRecorder counts queries per test and fails merge requests that raise the count ([GitLab docs](https://docs.gitlab.com/ee/development/database/query_recorder.html)). Second, CI that runs on the *merged* tree, which a merge queue builds as a temporary branch of base plus queued PRs ([GitHub Docs](https://docs.github.com/en/enterprise-server@3.14/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue), via search summary). Third, a single named owner for the database and query files. Fourth, a decision note recording why the index exists. In the C compiler run, new features "frequently broke existing functionality" until CI blocked regressions on every push, so the test-first defence has precedent at fleet scale ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)).

No study compares dividing LLM work by vertical slice with dividing it by layer, so this choice rests on inference. The reported successes all split work into **independently testable units with an oracle**: separate failing tests, separate target programs, separate files. When the C compiler's Linux task would not divide, the team used GCC as a known-good oracle so each agent hit different bugs ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). Cross-layer vertical slices work once the interfaces between layers are committed files; before that, each agent invents its own assumptions. Anthropic's docs recommend writing a SPEC.md and building from it in a fresh session "with a clean context and a written definition of done", with the reviewer pointed at the same spec (vendor guidance) ([Claude Code docs](https://code.claude.com/docs/en/best-practices)). MetaGPT's contract-first pipeline (requirements, then design, then API, then code) beat ChatDev on its authors' own benchmarks (measured, author-reported) ([arXiv 2308.00352](https://arxiv.org/pdf/2308.00352)). For a Godot UI the practical rule is that one agent owns the UI kit and theme while screen agents consume it read-only. Hotspot files (`project.godot`, autoload registries, theme resources, lockfiles, schema, route tables) each get one owner, or only the lead edits them. Claude Code's agent-team docs say it plainly: "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files" ([Claude Code docs](https://code.claude.com/docs/en/agent-teams)).

### A leased backlog with an idle queue removes both duplication and idle capacity

The large reported runs use pull systems. C compiler agents claimed a task by committing a text file to `current_tasks/`. A git push race forced the second claimant to pick another task, and a bash loop started a fresh session the moment one finished, so capacity never sat idle. Standing low-coupling roles (de-duplication, performance, documentation, design critique) soaked up spare agents (reported) ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). Anthropic's long-running harness kept **200+ features in JSON**, all initially failing. Agents could only flip a `passes` field ("It is unacceptable to remove or edit tests"), and JSON was chosen because models overwrite it less readily than Markdown (reported) ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Cursor's deadlocks show that claims need **leases that expire**, and a planner must keep refilling the queue ([Cursor](https://cursor.com/blog/scaling-agents)). Vague briefs cause duplication. In Anthropic's research system one subagent researched the 2021 chip crisis while two others duplicated 2025 work. Every brief needs an objective, an output format, tool guidance and boundaries (reported) ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). The idle agent in the last wave points to a missing refill path. The agents that stopped early point to stop rules nobody could misread (covered below).

### Repo files outperform relayed summaries and scheduled messages

Durable files passed by reference lose the least information. Anthropic had subagents write output to the filesystem "to minimize the 'game of telephone'" and pass lightweight references back. Early subagents "sent excessive updates that distracted other agents" (reported) ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). The C compiler fleet had no messaging at all. It coordinated through git, lock files, READMEs, progress files and a running document of failed approaches ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). For messages that must arrive, the documented primitives confirm delivery. Agent-team messages are reported as sent "only when the write to the recipient's mailbox file succeeds". `claude -p "msg" --cloud <id> --output-format json` returns `{ok:false, error}` on failure but "exits without waiting for a reply" (vendor docs) ([agent teams](https://code.claude.com/docs/en/agent-teams); [cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web)). Scheduled tasks give no delivery guarantee. When a task is disabled or paused it runs nothing. A "Succeeded" run "say[s] how the session ended, not whether Claude completed the work", and runs past the usage limit "are rejected until your usage window resets" ([Claude Code docs: scheduled tasks](https://code.claude.com/docs/en/routines)). The lost message from the last wave is therefore expected behaviour, not a bug. Any instruction that matters needs a positive acknowledgement: a status-file commit from the recipient within a deadline (inference).

### Disposable sessions need resumable repo state

Anthropic's long-running guidance treats every session as disposable. An initializer creates `init.sh`, a progress file and a first commit. Each later session reads the git log, progress notes and feature list, then runs a basic end-to-end check before starting new work, so it catches whatever the previous session broke. Observed failures included declaring the project done too early, running out of context mid-feature, and marking features done after only unit tests. The fixes were **one feature per session, a commit per feature, and end-to-end verification by driving the app** (reported) ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Claude Code's unattended-run checklist asks five questions: does the agent know what done looks like, can it check its own work, what may it touch, what stops it (`--max-turns`, `--max-budget-usd`), and where does the result go. A `Stop` hook exiting with code 2 sends the agent back to work until a check passes, overridden after eight consecutive blocks (vendor guidance) ([Claude Code docs](https://code.claude.com/docs/en/best-practices)). The docs also caution that "keep going" lines "are more likely to cause over-work than fix a stall" with current models.

Applied to this project's restart losses (inference): every long test run writes `test-results/<sha>.log` ending in a `DONE exit=<code>` line, and a restarted agent re-runs any test whose log lacks that line. While iterating, agents run a deterministic per-agent sample of the suite, like the C compiler's `--fast` 1–10% mode, and run the full suite only before marking a task ready ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). Each agent keeps `status/<agent>.json` on its branch with `task_id`, `state`, `last_green_sha`, `updated_at`, `expected_next_update_by` and `stop_at`. The lead then detects stalls with one `git fetch` and a JSON parse instead of reading transcripts. An agent is stalled only when `expected_next_update_by` has passed with no commit, which separates a stall from a long test run. Every deadline is written as, for example, `STOP_AT: 2026-11-02T18:00:00Z (= 13:00 America/New_York)`. At `STOP_AT` minus 30 minutes the agent starts no new task: it commits, pushes and writes `state: stopped` with a `next_step`. No source studies how agents misread zone-ambiguous times, so this protocol is inference.

### Shared usage limits need tiers, staggering and pause-safety

All sessions, subagents, scheduled tasks and claude.ai chat draw on one account's **five-hour window and weekly limit**. Max plans add a separate weekly limit for Fable ([Claude support](https://support.claude.com/en/articles/11145838-using-claude-code-with-your-pro-or-max-plan)). Anthropic publishes no token budget per window, and does not say how cache reads count against plan limits ([Claude Code costs](https://code.claude.com/docs/en/costs)). Since v2.1.234, `autoContinueAtUsageLimit` can wait for a reset and continue automatically, and switching model does not help once a session limit is hit ([Claude Code costs](https://code.claude.com/docs/en/costs)). A third-party claim of 5 concurrent sessions on Pro and 10 on Max is not documented by Anthropic ([Stoneforge](https://www.mintlify.com/stoneforge-ai/stoneforge/guides/scaling)). The workable approach is inference: measure burn per agent-hour from `/usage` early in the wave, and size concurrency to fit with 15–20% held back for the lead and recovery. Tier agents so the lowest tier checkpoints and stops first. Stagger heavy exploration phases. Avoid `/loop`, check-ins and cross-session messages that wake idle agents with a full-context resend. Because every agent commits after each verified step, a limit pause then costs wall-clock time but no work.

### Durable repo state is the memory that survives restarts

Knowledge has to live in git. Claude Code's auto memory is "machine-local… not shared across machines or cloud environments" ([Claude Code docs: memory](https://code.claude.com/docs/en/memory)). Context recall falls as context grows ("context rot"). Agents that write and re-read notes sustain multi-hour work: Claude playing Pokémon resumed long sequences after context resets by reading its own notes (reported) ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). CLAUDE.md should stay **under 200 lines**, since longer files "reduce adherence". Contradictory instructions get resolved "arbitrarily", and `/doctor prompt-audit` flags them. Path-scoped rules in `.claude/rules/` load only when matching files are touched, and anything that must always happen belongs in a hook, because memory is "context, not enforced configuration" (vendor guidance) ([Claude Code docs: memory](https://code.claude.com/docs/en/memory)). Teammates "don't inherit the lead's conversation history", so the spawn brief must carry the task specifics ([Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams)). That supports three layers (inference). The first is a short, stable CLAUDE.md. The second is decision notes and path-scoped rules that record *why* things exist ("index X serves query Y; guarded by test Z"). The third is per-agent handoff files, rewritten rather than appended to, carrying a `last_verified_sha` so readers know which commit the notes describe.

## Context size, not headcount, drives the token bill

Claude Code resends the whole conversation on every request and every tool round-trip, and the prompt cache serves the unchanged prefix. Opus 5.5 lists at **$4 per million input tokens and $20 output**. A cache read costs **$0.20, or 0.05× input**. A cache miss rewrites the prefix at **1.25× input on the 5-minute TTL or 2× on the 1-hour TTL**, so one miss costs 25–40 hits. Sonnet 5.5 costs exactly half of Opus ($2/$10, cache read $0.10). Haiku 5.5 costs $0.10/$0.50 under 100k tokens and five times that above ([Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). Matching needs "100 percent identical prompt segments" in the order tools, then system, then messages, and "there is no per-file or per-segment caching" ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)). The worked numbers below are inference at API list prices; plan-limit units are unpublished. One Opus 5.5 request at 350k context costs about **$0.07** in cache reads. Two hundred such requests read 70M tokens, about **$14**, against **$4** at a 100k average. A single cache miss at 350k costs **$1.75–$2.80**, the price of 25–40 normal requests. Cost per tool call therefore scales with context size, and session cost grows roughly quadratically with session length.

The 300k–400k sessions have a specific cause. Cloud sessions on native-1M models (Sonnet 5+, Opus 4.7+, Haiku 5.5, Fable) compact only near **967k tokens**. An earlier window can be set with `CLAUDE_CODE_AUTO_COMPACT_WINDOW` (range 100k–1M), or sessions capped at 200k with `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` ([Claude Code model config](https://code.claude.com/docs/en/model-config)). Compaction is lossy. It re-injects CLAUDE.md, the plan and up to five recent files, but a file over 5,000 tokens comes back only as a path, and nested CLAUDE.md files and hook-added context are only summarised ([Claude Code context window](https://code.claude.com/docs/en/context-window)). `/clear` "costs nothing". `/compact` is cheap while the cache is warm but costs the most when resuming an old session, because the history is reprocessed uncached ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)). The rule that follows (inference) is this. At a task boundary such as a PR pushed or a track merged, write a handoff file and start fresh. Continue or compact only when the next step depends on unwritten, fine-grained state such as a live debugging hypothesis. No controlled study compares quality after compaction with quality after a fresh session plus notes; Anthropic's context-rot guidance favours the smallest "set of high-signal tokens" ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

Several common actions break the cache: switching model ("each model has its own cache"), toggling fast mode, adding or removing MCP servers, compaction, removing accumulated images, and `opusplan`, which switches model on every plan-mode toggle. Editing repo files, CLAUDE.md, permission mode or skills does not. On a subscription within plan usage, the main conversation gets a 1-hour TTL while subagents get 5 minutes. Once usage spills into credits, Claude Code "drops the main conversation to the five-minute TTL" unless `promptCacheTtl` is set ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)). This matters for long test waits. A subagent that waits on a 25-minute suite returns to a cold cache, and on credits the main session does too. So route model choice by session, never mid-session, and set the 1-hour TTL explicitly if credits are enabled (inference).

### Subagents protect context but do not save tokens

A subagent can spend "tens of thousands of tokens" exploring and return 1,000–2,000 ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). It runs with its own cold cache on a 5-minute TTL and draws on the same usage pool. Explore runs on the parent's model unless `model:` or `CLAUDE_CODE_SUBAGENT_MODEL` says otherwise ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents)). Agent teams in plan mode use about **7× the tokens** of a standard session ([Claude Code costs](https://code.claude.com/docs/en/costs)). One practitioner measured 121k tokens for a task done inline against 513k when split across two subagents (anecdote) ([DEV Community](https://dev.to/nomurasan/i-measured-claude-codes-prompt-cache-cost-three-ways-85-of-it-wasnt-mine-to-trim-48hm)). The net saving is roughly the tokens kept out of the main context, multiplied by the number of later main-context requests, minus the subagent's own spend (inference). A 30k-token search result kept out of a session that makes 100 more requests saves about 3M cached reads, which justifies a Haiku search subagent. A small lookup needed at once is cheaper done inline.

### Model routing by session halves routine cost

Anthropic's guidance is that "Sonnet handles most coding tasks well", Opus should be reserved for "complex architectural decisions or multi-step reasoning", and simple subagents can run on `model: haiku` (vendor guidance) ([Claude Code costs](https://code.claude.com/docs/en/costs)). Launch coverage of Sonnet 5.5 reports it ahead of Opus 5.5 on Terminal-Bench 4.0 (**70.6% against 66.4%**; 63.6% against 59.6% in an independent run). It trails narrowly on CursorBench (55.5% against 57.8%) and more on "complex, open-ended work requiring sustained judgement" (secondary) ([aiweekly.co](https://aiweekly.co/alerts/introducing-claude-sonnet-55); [itdaily.com](https://itdaily.com/news/software/claude-sonnet-5-5/)). An aggregator reports SWE-Bench Pro at 81.3 against 89.9, which I could not verify ([apidog.com](https://apidog.com/blog/claude-sonnet-5-5-benchmarks/)). Two further points matter for routing. A model upgrade beat doubling the token budget in Anthropic's research system ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)), so a cheap model running longer is not a free substitute. And thinking tokens bill as output and cannot be turned off on 5.5 models, so `/effort` is the dial for simple work ([Claude Code costs](https://code.claude.com/docs/en/costs)). For this project the quality bar is the binding problem, so design and art judgement stay on Opus. Spec-following work against a frozen kit, which a gate will check, can move to Sonnet (inference).

### Test logs and screenshots are the cheapest tokens to remove

Anything added to context is re-read on every later request, so the cheapest savings come from filtering before content enters the context. A PreToolUse hook that pipes test output through `grep -A 5 -E '(FAIL|ERROR|error:)' | head -100` cuts a 10,000-line log "from tens of thousands of tokens to hundreds" ([Claude Code costs](https://code.claude.com/docs/en/costs)). Images cost ⌈w/28⌉×⌈h/28⌉ tokens. A 1920×1080 screenshot costs **2,691 tokens** against about **700 at 960×540**, and the high-resolution tier caps at 4,784 per image ([Anthropic vision](https://platform.claude.com/docs/en/build-with-claude/vision)). Twenty 1080p screenshots left in context add about 54k tokens to every later request. When Claude Code drops old images, "the next request reprocesses the conversation from the earliest of those messages onward", which is a full cache miss ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)). Anthropic warns that downscaling "might… make text less legible". No study measures visual-QA quality against resolution, so fine-text legibility checks should use full-resolution crops of the relevant region rather than downscaled full screens (inference).

### Measured savings are few, and naive trimming can backfire

Rigorous fleet-level case studies do not exist. Practitioner data consistently finds the cache dominates the bill. One author found **89%** of a coding-agent bill was cache traffic ([levelup](https://levelup.gitconnected.com/89-of-my-coding-agent-bill-was-cache-traffic-and-most-token-saving-tools-cannot-reach-it-a5c6eb314c9e)), and a preprint estimates caching cut realised cost by **88.6%** against nominal input rates ([arXiv 2607.13080](https://arxiv.org/pdf/2607.13080)). The cautionary result comes from 2,848 billed runs: a tool-output compression layer removed **38% of tool-output tokens yet raised paired cost 6.8%**, because it rewrote cached history ([danielvaughan.com](https://codex.danielvaughan.com/2026/07/28/token-reduction-is-not-cost-reduction-prompt-cache-economics-codex-cli-tool-output-compaction-billing/)). All three are search-summary readings. Anthropic's enterprise baseline is about **$13 per developer per active day**, under $30 for 90% of users ([Claude Code costs](https://code.claude.com/docs/en/costs)). The ranking below is my synthesis.

| Lever | Expected effect | Quality risk |
|---|---|---|
| Auto-compact window ~200k plus fresh session per task with handoff | ~3× cheaper requests versus 350k; better recall | Low if handoff notes are good |
| No mid-task cache breaks (model switches, MCP toggles, `opusplan`); 1h TTL on credits | Avoids 25–40× miss penalties | None |
| Sonnet 5.5 for spec-following sessions | ~2× cheaper | Low with an independent gate; higher on judgement work |
| Filter test output; downscale or delegate screenshots | Removes tens of thousands of tokens per later request | Low; use full-res crops for text checks |
| Haiku 5.5 subagents (under 100k) for search and log triage | 40× cheaper input than Opus | Low for retrieval; do not use for verdicts |

## LLM judges need pass/fail anchors and owner calibration before they can gate

Strong LLM judges reach human-level agreement on **pairwise** preferences: GPT-4 agreed with humans over 80% of the time on MT-Bench (measured) ([Zheng et al.](https://arxiv.org/abs/2306.05685)). They are much weaker at **absolute scores on a scale**, which is the art director's current 0–5 × 14 rubric. Judges with 80%+ percent agreement can still be about **20 points apart** in assigned scores. Even the best judges reached kappa of about 84 against a human–human 96, and they "tend to be lenient" (measured, via search summary) ([Thakur et al.](https://arxiv.org/html/2406.12624v1)). One survey cites LLM-to-human correlations of **0.3–0.6** against human-to-human 0.8–0.9, and an evaluator that caught over 95% of good items but **only 30–60% of bad ones** ([Eugene Yan](https://eugeneyan.com/writing/llm-evaluators/)). Multimodal judges show the same split. GPT-4V's pairwise agreement with humans was **0.773** (no ties), against a Pearson **0.490** for absolute scoring. Several models "mostly assign scores around 4, rarely 1 or 2" (measured, via search summary) ([MLLM-as-a-Judge](https://arxiv.org/abs/2402.04788)). A 2025 mobile-UI study found near-perfect zero-shot agreement (κ ≥ 0.81) on *visual* dimensions such as aesthetics. The same models overestimated usability and were unreliable on interaction-dependent judgements from static screenshots, and few-shot prompting *worsened* agreement ([ACM DL](https://dl.acm.org/doi/10.1007/978-3-032-30549-7_12), via search summary). Judges are also noisy run to run: three repeated scores of the same output agreed in only **68.6%** of cases in one study ([arXiv 2607.13347](https://arxiv.org/pdf/2607.13347)).

The mitigations with evidence are specific. Removing criteria and reference answers causes the largest drop in human correlation, and describing only the extreme anchors works about as well as describing every level. Averaging several samples beats a single greedy score (measured, via search summary) ([arXiv 2506.13639](https://arxiv.org/html/2506.13639v1)). A panel of smaller models from *different families* beat a single GPT-4 judge at 7–8× lower cost ([PoLL](https://arxiv.org/abs/2404.18796)). Anthropic recommends grading "each dimension with an isolated LLM-as-judge", letting the judge return "Unknown", and calibrating against human graders. It also cautions against reading scores "at face value until someone digs into the details… and reads some transcripts". Grader fixes alone took Opus 4.5 from 42% to 95% on CORE-Bench (reported) ([Anthropic](https://anthropic.com/engineering/demystifying-evals-for-ai-agents)). Hamel Husain's method has a domain expert label pass/fail with a written critique and splits the labels into train, dev and held-out test sets. It reports **true-positive and true-negative rates separately**, because a rubber-stamp judge scores 90% agreement when 90% of items pass. The Honeycomb case reached over 90% expert agreement in about three iterations (opinion, secondary) ([hamelsmu/evals-skills](https://github.com/hamelsmu/evals-skills/blob/main/questions.md); [Latent Space](https://latent.space/wiki/hamel-husain/)). One secondary source says fewer than about 60 labels leaves confidence intervals too wide to act on ([knomit](https://knomit.io/blog/unattended-llm-judges/)). The owner's bar will also move as they see outputs. EvalGen found "grading outputs helps users define criteria" ([Shankar et al., UIST 2024](https://arxiv.org/abs/2404.12272)), so rubric versions must be logged.

Applied to the art director (inference), the 14 qualities fall into three groups. **Deterministic** qualities move to scripts: resolution, safe areas, touch-target size, text overflow at target widths, contrast, palette. **Static visual** qualities become one isolated judge call each, phrased as pairwise "at least as good as golden screen X on this quality?", sampled three times, blocking only on a confident fail and sending split results to an exception queue. **Interaction-dependent** qualities (motion, game feel, flow) go to captured-frame review or the owner, because static-screenshot judges overrate them. Every model in Claude Code is from one vendor, so the cross-family panel the evidence prefers is not available. The nearest substitutes are four: a different model from the producing agents, no access to the producer's reasoning, owner-approved golden references as the bar, and a measured catch rate on held-out owner labels.

### Owners catch more by reviewing plans and samples than streams

Per-item approval decays into rubber-stamping. Claude Code users accept **93%** of permission prompts ([Anthropic](https://anthropic.com/engineering/claude-code-auto-mode)). Later reporting cites **97%** of prompts accepted but **39% of plans rejected**, so people scrutinise plans far more than individual actions (secondary) ([TechWyse](https://www.techwyse.com/news/platform-updates/anthropic-claude-code-auto-mode-default)). In a reported study of 1,053 testers, humans caught a planted dangerous command only **13.6%** of the time, while a classifier blocked 89% (secondary press) ([The Register](https://www.theregister.com/a/5285326)). Reviewers approved about **78%** of subtly subverted AI plans (cited secondhand) ([NeuralTrust](https://neuraltrust.ai/blog/human-in-the-loop-ai-agents)). Owner time therefore goes furthest on high-leverage, information-dense decisions (inference). Those are, first, the golden set and rubric anchors that every automated gate enforces. Second, the wave plan and contracts. Third, pairwise "candidate against golden" boards per screen family. Fourth, a blind weekly audit of a random sample of the gate's *passes*, which measures the judge's catch rate and its drift. The 80–99% against ~30% gap is also the METR pattern. Agent work that passed algorithmic tests was often unusable on manual review, and METR concluded that algorithmic scoring "may overestimate AI agent real-world performance" (measured, small sample, via search summary) ([METR](https://metr.org/blog/2025-08-12-research-update-towards-reconciling-slowdown-with-time-horizons)). Progress should be reported as the count of items passing the owner-calibrated gate. Where consistency matters, use pass^k: at 75% per-trial success, three consecutive passes happen only about 42% of the time ([Anthropic](https://anthropic.com/engineering/demystifying-evals-for-ai-agents)).

## Operating model for the next UI wave

The wave has seven builder roles and about 158 agent-hours, with the lead's hours on top. The plan below follows the evidence in four ways. The UI kit contract and golden set are frozen before screens start in parallel, because UI is the high-coupling "Flappy Bird" case. Builder sessions are capped at **five at once**, the top of Anthropic's 3–5 teammate guidance, because the weekly limit is close and one lead must validate everything. Model choice follows judgement load. And owner time goes to calibration and samples, not streams. The hour split per role and phase is my allocation and should be adjusted to the actual backlog.

### Roles, models and hours

| Role | Model (per session, never switched mid-session) | Agent-hours | Notes |
|---|---|---|---|
| Lead / integrator | Opus 5.5, medium effort | Outside the 158; reserve 15–20% of budget | Fresh session per integration cycle, reading status files; plans, triages, runs the merge queue; does not hand-resolve conflicts |
| Art director: direction and golden set | Opus 5.5 | 6 (Phase 0) | Converts the 14-quality rubric into deterministic checks, pairwise visual checks and owner-reviewed checks; drafts golden-set candidates |
| Art director: gate runs | Fable 5.1 if it shows the highest catch rate on the held-out owner labels; otherwise Opus 5.5 | 16 (Phases 1–3), in short read-only runs | A different model from the artists reduces self-preference; on Max plans Fable draws a separate weekly limit (inference: verify against the golden set first) |
| UI artist ×2 | Opus 5.5 | 44 (22 each) | Judgement-heavy visual work, where Sonnet trails |
| Kit / pipeline engineer | Opus 5.5 for contract and component API (Phases 0–1); a fresh Sonnet 5.5 session for maintenance (Phase 2) | 26 | Sole owner of theme, kit components, import pipeline and kit-related hotspot files |
| Screen agent ×3 | Sonnet 5.5, medium effort; a screen that fails the gate twice gets a fresh Opus 5.5 session | 66 (22 each) | Build against the frozen kit and golden screens; read-only on kit |
| Subagents (search, log triage) | Haiku 5.5, under 100k tokens | Small | Never used for gate verdicts |

### Phases and concurrency

| Phase | Running builders (max) | Agent-hours | Approx. wall-clock | Exit criterion |
|---|---|---|---|---|
| 0. Calibrate and freeze | 2 (art director, kit engineer) | 14 | ~8 h | Owner has labelled 30–60 golden items; judge meets catch-rate target on held-out third; kit contract, ownership map and leased JSON backlog committed; database query-count guard test merged |
| 1. Foundations | 4 (kit engineer, 2 artists, 1 pilot screen) plus gate runs | 43 | ~12 h | Kit components pass their checks; pilot screen built only from the kit passes the gate and the owner's pairwise board |
| 2. Screens at width | 5 (3 screens plus 2 shared by artists and kit) plus gate runs | 71 | ~15 h | Every screen passes deterministic and judge gates; exceptions resolved |
| 3. Polish and harden | 5 (3 screens, 2 artists) plus gate runs | 30 | ~6 h | Owner's milestone board approved; blind audit of passes completed |

The total is about **40 wall-clock hours** at this cap. Two rules from the evidence govern scaling. Do not raise the cap because agents are idle: refill them from the idle queue (asset-import checks, tests, localisation-overflow sweeps, kit documentation). And drop to three builders if early burn says the weekly budget will not hold, rather than letting all of them stall together. Before Phase 1, read `/usage`, compute the share of the weekly bar each agent-hour uses by model, and project Phase 1–3 spend plus a 20% reserve. If it does not fit, the owner chooses between waiting for the weekly reset before Phase 2, enabling usage credits (and setting `promptCacheTtl: 1h`), or cutting scope. Tier sessions so that, as headroom shrinks, the idle queue checkpoints and stops first, then the artists' secondary assets, and the lead, kit and gate stop last.

### Gates and cadence

Each item passes four gates in order of cost. G0 is deterministic: Godot headless scene smoke test, captures at target device sizes, asset specification checks, safe-area and touch-target checks, text-overflow and contrast checks. G1 is the independent art-director judge: read-only tools, one isolated call per static visual quality, pairwise against the golden screen, three samples, "Unknown" allowed, a block only on a confident fail, and split verdicts sent to the exception queue. G2 is the lead's merge queue, with CI on the combined tree, including the query-count guard and the regression suite. G3 is the owner's sample. A worker marks a task ready only after rebasing onto main and passing G0 and G1 on its branch. Its self-assessment is recorded as a claim with attached evidence and never counts toward any gate.

Workers take one backlog task per session from the leased JSON backlog. My suggested defaults are a three-hour lease, renewed by a status commit; a status update at each checkpoint, at least every 45 minutes; and a fresh session with a handoff file at each task boundary. Every session runs with `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000`, the test-output filter hook, screenshots at about 960 px on the long edge for triage, and full-resolution crops for text checks. Tests log to files with completion markers, and deadlines are written as ISO 8601 with an explicit offset, enforced by a Stop hook. The lead keeps the hourly integration slot only as a *maximum* merge latency, merging ready PRs one at a time as they arrive. It commits an hourly status file that links to the backlog and status JSON rather than paraphrasing them. It sends the owner a digest at each five-hour window boundary, and alerts immediately only on a stall past `expected_next_update_by`, a gate disagreement, or remaining usage below the reserve. Any instruction to a worker counts as delivered only when the worker's acknowledgement commit appears. Scheduled tasks are checked for enabled state and transcript before anyone relies on them.

### Owner approvals

| When | What the owner does | Time | Why |
|---|---|---|---|
| Before Phase 0 ends | Labels 30–60 golden items pass/fail per quality with a one-line critique, deliberately including clear fails and borderline cases; approves the rubric anchors | ~60–90 min | Sets the bar every gate enforces; needed for catch-rate measurement |
| Before Phase 1 | Approves the wave plan, kit contract, ownership map and budget choice | ~20 min | Owners reject plans 39% of the time, so plans are where review pays |
| End of Phase 1 | Pairwise board: pilot screen and kit against golden screens | ~15 min | Catches contract or style errors before three screens copy them |
| Per screen family (Phases 2–3) | Pairwise board of 5–10 items; everything else merges by default after 24 h unless the owner objects | ~15 min each | Avoids rubber-stamp streams |
| Daily during the wave | Clears the exception queue (split judge verdicts, "Unknown", interaction-dependent qualities) | ~10–20 min | Exceptions are where judges are least reliable |
| Weekly and at wave end | Blind audit of 10–20 random gate *passes* on the same form | 15–20 min | Measures the judge's catch rate and drift; triggers recalibration |

The default-merge rule is safe only while the blind audit confirms the gate's catch rate. If the audit finds failures the gate passed, the judge's prompt is revised against those critiques and re-validated on the held-out set before default merges resume. Recalibration is also triggered by a judge-model change, a rubric edit or a new screen type.

## Conclusion

The last waves did not fail for lack of agents. They failed because self-assessment substituted for measurement, unwritten design decisions substituted for contracts, and long conversations substituted for durable state. The most useful finding is that one change fixes the quality, cost and continuity problems together: moving truth out of agent conversations and into the repository and gates. A committed contract prevents collisions and lets a cheaper model build screens. A handoff file makes restarts idempotent and lets contexts stay at 200k instead of 400k. A calibrated, independent gate turns "80–99% done" into a count the owner can trust and makes default-merge safe. Concurrency then becomes a budget decision rather than an organisational one.

Two uncertainties should shape how the owner reads results. First, no published source measures plan-limit consumption in tokens or tests LLM-judge reliability on stylised game UI. The first hours of the wave are therefore an experiment, and the owner should treat the burn rate and the judge's held-out catch rate as the two numbers that decide whether to widen, narrow or pause. Second, since every available judge comes from the same vendor as the builders, the owner's labelled golden set is the only fully independent signal in the system. It deserves more owner time than any individual approval.
