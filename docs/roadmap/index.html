F15's recommendation was to give Response an effect that works without a guard, using the two things §13.2 names and never defines: the Spire's reach and the guardian Sage's single power. Guards and response are the island's only detect-and-act chain — the other three layers work by delay, and delay reaches an outcome only through a clock with four times the slack it would need. Architecture: one-way data, typed layers, a design that lands in one place

Done from here

The market-standard shape for a mobile game client, in Godot's own terms. Views (scenes) only draw and send intents. Presenters are plain GDScript classes that turn state into what a view shows, with no nodes, so they are tested headless. One store holds the app's state and changes only through actions a reducer applies (unidirectional data, as Redux and The Composable Architecture do it), and keeps the last actions in a ring buffer, so a defect report carries the steps that caused it. Specify pathfinding and crew control before building it

Under way from here

The largest gap and the system most likely to fail §30.7's premise 3 — that delegated control still feels like agency. Drafted in spec/movement.md; make felt control a gate on the slice, not a polish item.

The buildable half is built. sim/path.rs is §12.18's pathfinder: breadth-first, four neighbours in a fixed north-east-south-west order, ties by tile index. Breadth-first rather than A* because A*'s answer depends on the heuristic and on how a priority queue returns equal keys — two places correct implementations differ. Terrain slows the walk and cannot bend the route, which is the spec's rule: a pathfinder that went round mud would be choosing for the player.

§12.18's four behavioural clauses are tests rather than prose — no re-routing, no picking a different door, crew pass through one another, the command and never the path.
