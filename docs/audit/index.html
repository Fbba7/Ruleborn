What changed about the approach

Deviations from the plan the design document sets out, each with what it costs and why it was worth it.

D1

The build-willingness test runs first, not second

change Adopted
§26.7§13.3§30.8

§26.7 schedules the paper heist first and the build-willingness test after it. But the build test is ranked risk #1, and §26.7 itself calls it “the single decision that changes the most”. The heist test decides whether the game is fun; the build test decides what game is being built — authorship, authorship-with-scaffolding, or a pivot to generated islands the player curates.

→ Run both in parallel. Neither blocks the other, and the build test's answer changes what the rest of the plan is for.

D2

The paper prototype became a browser prototype

change Done
§19.27§26.7§25.5

Both pre-code gates as written assume about thirty people in a room — eight to twelve for the paper heist, fifteen to twenty for the build test. That cohort does not exist for this project. The questions did not change; the method did, because a link can be sent to strangers and a room cannot. §25.5 already budgets for recruited remote panels, so the route was costed.

→ Built and published. It also answers a question paper could not: whether a delegated crew feels like playing or watching (§30.7 premise 3), which cannot be tested on a board where a human moves the pieces.

v3.0 Overtaken. §19.27 now answers every pre-code question by simulation rather than by people, so the published prototype is no longer on the critical path. It still runs, and it is still the only artefact that can answer the one question §19.27 says simulation cannot. See D20.

D3

The prototype sits ahead of the determinism spike on the critical path

change Adopted
§26.7§24.2§26.5

§26.7 puts the determinism spike immediately after the paper tests. Because the paper test became software, a few working sessions of engineering now precede the spike — exactly what the paper test was designed to avoid.

→ Accepted: §26.5's own rule is that scope is the lever, and buying the two project-deciding answers cheaply is worth it. This does not relax the rule that gameplay code waits for the spike. The prototype is throwaway and written as such.

D4

§26.7 goes spike → lock the simulation contract → lock detection → lock the law schema → lock saves. Every one of those assumes there is one specification to lock. Four systems currently have two (C1, C2, C3, C6), and a fifth has two budgets (C5).

→ Work the blocking half of this register before any lock. It is days of desk time and the cheapest work in the whole plan.

D9

change Proposed
§26.8§19.17§26.5

§26.8 estimates ~270 agent runs (≈810 focused hours) and then states plainly that the iteration needed to find the fun is unbudgeted. D16

The Vault’s load rate is cut fivefold, from 150 a second to 30

change Proposed
§12.6§11.1§9.4

§12.6’s 150-loot-a-second is a published number and this changes it to 30 for Carriers and 8 for everyone else, with every role able to load rather than Carriers only. The reason is F5: at 150 a second the phase the document calls its central decision is two seconds long and has one option.

The replacement rate is not a guess. §12.6 sets its own target of one decision every 8–12 seconds, and a loading window shorter than one decision cannot contain a decision; 30 a second puts a full crew load at exactly ten. The rate scales with character level alongside Carry (§11.4), so the ten seconds holds for the whole game.

→ Accepted in docs/design/spec/vault.md, flagged for sign-off because it is a large move on a published figure. The only alternative that preserves the decision is raising carry capacity fivefold, which breaks §9.4’s exposure percentages and §11.1’s role balance instead. Doing neither means deleting the sentence that calls the Vault phase a decision.

D17

change Proposed
§12.8§11.1

§12.8’s ambush is triple Power. F4 measures what that delivers: the same section’s claim that two ambush hits drop an equal-level guard is true for three of twenty-five pairings. This adds a floor — an ambush deals triple Power or half the target’s maximum health, whichever is greater — which changes a formula the document states in order to satisfy a rule the document also states.

G1

Pathfinding and crew movement

unspecified Fixed in v3.0
§12.5§12.6§12.7§6§30.7

The document specifies in detail what guards perceive and what laws do to movement parameters, but never how a crew actually moves. Unanswered: is the world a tile grid or continuous (§6 is in tiles, §12.17's sub-metre zones and degrees-per-tick imply continuous); how does a player order movement at all (§12.7 covers abilities, never locomotion); what happens at an unplanned fork; how do 3–5 crew avoid each other; does the §12.5 route planner produce a literal path or waypoints re-pathed at runtime — which have very different determinism properties.

→ Drafted. docs/design/spec/movement.md, which unlike the other spec files is partly new design, since the document leaves this empty. It settles the world model first — tile topology, continuous position, which is the only reading that satisfies both §6's per-tile terrain and §12.17's sub-metre vision zones and degrees-per-tick turning — then proposes tap-to-move with per-member selection, deterministic breadth-first pathfinding with a fixed neighbour order, and commands rather than paths in the input log (§24.10).

The rule that protects premise 3 is stated explicitly: the crew never makes a decision the player did not make. No auto-attack, no auto-avoid, no auto-retreat, no re-routing around a guard the player walked them into. A unit cannot look stupid for a decision it never made. The prototype implements this and the felt-control question is measured directly against §30.8's 70% threshold.

v3.0 §12.18 settles it, and adopts the reading in spec/movement.md: tiles for terrain and building, continuous millitile position and facing, breadth-first pathfinding with a fixed neighbour order, the command recorded rather than the path, and crew passing through one another. The rule that protects premise 3 is stated as a heading: the crew never makes a decision the player did not make.
