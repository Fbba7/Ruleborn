What changed about the approach

Deviations from the plan the design document sets out, each with what it costs and why it was worth it.

D1

The build-willingness test runs first, not second

change Adopted
§26.7§13.3§30.8

§26.7 schedules the paper heist first and the build-willingness test after it. But the build test is ranked risk #1, and §26.7 itself calls it “the single decision that changes the most”. The heist test decides whether the game is fun; the build test decides what game is being built — authorship, authorship-with-scaffolding, or a pivot to generated islands the player curates.

→ Run both in parallel. Neither blocks the other, and the build test's answer changes what the rest of the plan is for.

D2

The paper prototype became a browser prototype

change Done
§19.27§26.7§25.5

Both pre-code gates as written assume about thirty people in a room — eight to twelve for the paper heist, fifteen to twenty for the build test. That cohort does not exist for this project. The questions did not change; the method did, because a link can be sent to strangers and a room cannot. §25.5 already budgets for recruited remote panels, so the route was costed.

→ Built and published. It also answers a question paper could not: whether a delegated crew feels like playing or watching (§30.7 premise 3), which cannot be tested on a board where a human moves the pieces.

v3.0 Overtaken. §19.27 now answers every pre-code question by simulation rather than by people, so the published prototype is no longer on the critical path. It still runs, and it is still the only artefact that can answer the one question §19.27 says simulation cannot. See D20.

D28

The job that keeps the playable build current ran, reported success, and published nothing

change Done
§30.18§26.7§19.27

The prototype is the only artefact anyone outside this repository can actually touch, so an hourly Routine republishes it when the branch moves. It fired, took fifty-eight seconds, and was recorded SUCCEEDED. The published page did not change. Two faults, either one fatal on its own.

It could not tell new from old. The job compared the prototype’s last commit date against the artifact’s publish date, and Artifact action: "list" reports only a calendar day. A commit and a publish on the same day are indistinguishable — so from the first day the two coincided, which was the day it was written, the job would have answered already current for ever.

It could not publish. Artifact action: "read" saves the live page to a file and counts the version as viewed only once every line of it has been read. The prompt said to read it; it did not say that a partial read does not count. So the read was partial, the publish was refused, and the turn ended without error.

The second is the same shape as D24–D26 wearing different clothes, and it is the one worth keeping: a job that cannot fail cannot be trusted when it passes. Nothing threw, so nothing was reported, so the artifact sat a day behind the code while the dashboard read green.

→ Both fixed. The page now carries a BUILD stamp — a digest of itself with that line removed — so the job compares the published page against the current page instead of comparing two dates: is the published page this page? build_prototype.py --stamp prints it, --self-test proves it still moves when the page moves, and both are build gates. The prompt now spells out the full-read requirement, and a final step requires the publish to report a new version number before the run may claim to have worked.

Generalised since: tools/build_stamp.py stamps all three published pages — the prototype, this register and the roadmap — and holds each one’s path and artifact URL, so the job reads what to publish rather than carrying a hard-coded list. The prototype keeps its stamp as a JavaScript constant because it shows it on screen; the two generated pages carry an HTML comment. One digest function strips either form, because two implementations of a stamp would be the very fault this register exists to record.

The general rule, alongside D27’s: an automated job needs a check that its work landed, not just that it ran.

D25

No crew in the harness could see §5.4’s clock, so nothing priced in time could be measured at all

change Done

Chasing the clock — the dial F15, F16, F18 and F20 all point at — the first experiment was to shorten §5.4’s clock and watch the stopping decision move. It did not move. → Competent and Optimal crews now leave when the time left no longer covers the walk home, estimated the way a player would estimate it — the way out is the way in, so what it cost to reach the Vault is what it will cost to leave, plus 15%. Careless still ignores it, which is what makes it careless.

The margin is chosen, not derived, and it is the one number here to playtest rather than to trust. It is also biased in a known direction: the way in is crouched and routed around cones, the way out is a run, so estimating the walk home from the inbound time makes crews leave earlier than they need to. That is the conservative direction for everything measured through it.

The structural guard is a fingerprint. Both of this session’s harness faults were found by reading the model, not by anything going red, because every other test in the suite asserts a band rather than a value — which is right for a finding and useless for a silent change. test_the_harness_gives_the_same_answers_as_when_it_was_last_read hashes the grade, length, fill, decision count and alarm of 40 runs. A deliberate model change updates the digest and says what moved; anything else is a change nobody meant.

F14, F18, F19 and F20 were all re-measured through it.
